# ADR-0008 — Tool Calling Architecture

**Status:** Accepted
**Date:** 2026-07-18
**Author:** Sentri V2

---

## Context

Sentri V2 decommissioned continuous filesystem observation (ADR-0006) in favour of on-demand environment access. The question became: **how should the reasoning model invoke local workspace operations, and where does the execution loop live?**

Three design options were considered:

1. **Separate Agent Layer** — A dedicated `AgentOrchestrator` class sits between `ConversationEngine` and the reasoning provider, intercepts tool calls, executes them, and manages the multi-turn loop.
2. **Pipeline Worker** — A new `tool_worker` async task runs alongside `llm_worker`, `speech_planner_worker`, and `tts_worker` in the streaming pipeline.
3. **Inline in the Reasoning Provider** — The `OllamaReasoningProvider.stream()` method handles tool detection, execution, and re-querying internally before yielding any text tokens.

## Decision

Option 3: **tool calling is implemented inline within the reasoning provider**.

The `OllamaReasoningProvider.stream()` method operates as follows:

```
for turn in range(5):                    ← max 5 tool-calling rounds
    POST /api/chat (stream=False)        ← non-streaming request with tools
    if response contains tool_calls:
        execute tools via TOOL_REGISTRY
        append results to message history
        continue                          ← re-query Ollama
    else:
        yield final text word-by-word     ← simulate streaming
        return
```

### Key Design Choices

1. **Non-streaming during tool turns**: Ollama streams tool call arguments as fragmented JSON deltas, which are complex and error-prone to reassemble. By using `stream: False` during tool-calling rounds, we get complete, parseable JSON in a single response. The latency cost is negligible (~300-600ms for a 4B model generating a tool call).

2. **Simulated streaming for the final response**: Once all tools have executed and Ollama produces a text-only response, the provider yields it word-by-word with a 20ms inter-word delay. This allows the downstream `SpeechPlanner` and TTS to begin synthesis immediately, preserving the low-latency streaming behaviour for voice turns.

3. **5-turn limit**: Prevents infinite tool-calling loops. In practice, most queries resolve in 1-2 tool calls.

4. **Schema/Registry split**: Tool definitions are separated into two files:
   - `app/tasks/tool_schemas.py` — 13 JSON schemas in Ollama's native tool format (passed to the model)
   - `app/tasks/task_registry.py` — `TOOL_REGISTRY` mapping tool names to Python functions (used for execution)

   This separation means the model sees declarative schemas, while execution is handled by a flat function map with no framework overhead.

5. **Both endpoints**: Tool calling is supported in both the text path (`ConversationAdapter.generate_async`) and the voice path (`OllamaReasoningProvider.stream`), using the same `TOOL_SCHEMAS` and `TOOL_REGISTRY`.

## Motivation

- **Simplicity**: No new classes, no new workers, no new async coordination. The tool loop is a `for` loop inside an existing method.
- **Provider encapsulation**: Tool execution is invisible to the pipeline, the engine, and the WebSocket handler. They see only the final text tokens — exactly as if the model had answered without tools.
- **Provider independence** (ADR-0007): ASR and TTS providers are completely unaware that tool calling exists. Only the reasoning provider interacts with tools.
- **Robustness**: Non-streaming tool calls eliminate all JSON fragment reassembly bugs. The 5-turn cap prevents runaway loops.

## Consequences

- The reasoning provider is no longer a pure LLM proxy — it has execution side effects (filesystem reads, web searches, memory writes). This is an intentional trade-off for simplicity.
- Adding a new tool requires two changes: a schema in `tool_schemas.py` and a function in `task_registry.py`. No pipeline or engine changes.
- The `websocket` parameter is threaded through the call chain so tool execution logs (`TOOL_CALL`, `TOOL_RESULT`) can be sent to the frontend in real time. This parameter is optional and `None`-safe.
- If a future model supports native streaming tool calls reliably, the non-streaming fallback can be replaced without changing any code outside `reasoning.py`.

## Compliance Rule

> Tool execution is encapsulated inside the reasoning provider. No other component in the pipeline is aware of, or participates in, tool calling. Adding a tool never requires changing the pipeline, engine, or transport layers.
