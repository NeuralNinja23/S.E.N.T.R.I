# ADR-0005 — Conversation Model Development

**Status:** Accepted
**Date:** 2026-07-09
**Author:** Sentri V2

---

## Context

Sentri's long-term goal is to develop and improve its own conversation model — whether that means fine-tuning an existing model, training from scratch, or replacing the current model entirely with a better one.

The question this ADR answers is: **where does model development work live, and what is its relationship to Sentri's inference stack?**

This ADR is intentionally model-agnostic. Today the active model is MiniOmni2. Tomorrow it could be MiniOmni3, GLM Voice, Sentri Voice V1, or a completely custom architecture. The boundary defined here applies regardless of which model is in use.

## Decision

Model development code (fine-tuning scripts, training configs, data preparation, export pipelines) lives **alongside the model it operates on**, in a directory owned and controlled by the Sentri project.

The current instance:
```
GenxAI Labz/
└── MiniOmni 2/               ← private copy, no upstream remote
    ├── server.py              ← inference server (unchanged)
    ├── model.py               ← model architecture
    │
    └── sentri_training/     ← development code
        ├── prepare_data.py
        ├── fine_tune.py
        ├── configs/
        └── artifacts/         ← trained weights
```

**Sentri's inference stack (`config.py`, `InferenceRuntimeManager`, `InferenceRegistry`) does not change when a new model is trained.** The trained weights land in the same location the inference server already loads from.

When a new model generation requires a new location, only `MINIOMNI_HOME` (or an equivalent config key) changes. No conversation, API, or runtime code changes.

## Motivation

- The architectural boundary — not the current model — is what this ADR protects.
- Keeps model development concerns completely separate from inference concerns.
- `InferenceRegistry` already supports registering any new model by ID. Switching to a new model is a config change, not a code change.
- Model development teams (or future contributors) can work on training without touching Sentri's backend codebase at all.

## Consequences

- Training scripts read data from Sentri's SQLite database via a file path (env var or argument). They never import from `backend/`.
- Sentri's inference stack is completely unaware that training happened.
- If a new model requires a fundamentally different runtime (e.g. a local Python process instead of a Flask server), that is handled by adding a new `ISpeechToSpeechModel` implementation and registering it — not by modifying existing components.
- `SessionMetrics` and conversation `events.py` are the intended data sources for training signals. Persistence hooks for these will be added when the training pipeline matures.

## Compliance Rule

> Model development lives with the model. Sentri's inference stack depends on abstractions, not implementations. Swapping a model never requires changing the conversation, API, or runtime layers.
