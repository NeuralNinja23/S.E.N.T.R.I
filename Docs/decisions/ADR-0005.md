# ADR-0005 — Conversation Model Development

**Status:** Accepted
**Date:** 2026-07-09 (Updated: 2026-07-18)
**Author:** Sentri V2

---

## Context

Sentri's long-term goal is to develop and improve its own conversation model — whether that means fine-tuning an existing model, training from scratch, or replacing the current model entirely with a better one.

The question this ADR answers is: **where does model development work live, and what is its relationship to Sentri's inference stack?**

This ADR is intentionally model-agnostic. Today the active reasoning model is `Qwen3.5-4B-Uncensored` served via Ollama. Tomorrow it could be a fine-tuned variant, a larger quantised model, or a completely custom architecture. The boundary defined here applies regardless of which model is in use.

## Decision

Model development code (fine-tuning scripts, training configs, data preparation, export pipelines) lives **outside the Sentri backend codebase**, in a dedicated workspace or repository.

The current model stack:
```
Ollama (system service)
└── Qwen3.5-4B-Uncensored (Q4_K_M quantisation)
    └── Pulled from: hf.co/HauhauCS/Qwen3.5-4B-Uncensored-HauhauCS-Aggressive

Sentri Backend
├── .env                         ← REASONING_MODEL config key
├── app/conversation/adapter.py  ← text reasoning via Ollama HTTP API
└── app/conversation/streaming_pipeline/
    └── providers/reasoning.py   ← streaming voice reasoning via Ollama HTTP API
```

**Sentri's inference stack (`config.py`, `InferenceRuntimeManager`, `InferenceRegistry`) does not change when a new model is trained or swapped.** Switching reasoning models requires only changing the `REASONING_MODEL` environment variable in `.env`. No conversation, API, or runtime code changes.

For ASR and TTS (Faster-Whisper and Kokoro ONNX), model weights are downloaded automatically by `InferenceRuntimeManager` at first startup and cached locally. Swapping ASR or TTS models requires updating the provider driver and potentially the model name — but never the pipeline or engine.

## Motivation

- The architectural boundary — not the current model — is what this ADR protects.
- Keeps model development concerns completely separate from inference concerns.
- `InferenceRegistry` already supports registering any new model by ID. Switching to a new model is a config change, not a code change.
- Model development teams (or future contributors) can work on training without touching Sentri's backend codebase at all.
- Ollama's model management (pull, list, delete) is handled by the `ollama` CLI, keeping weight management out of the application entirely.

## Consequences

- Training scripts and data preparation tools do not live in `backend/`. They never import from the Sentri application.
- Sentri's inference stack is completely unaware that training happened.
- If a new model requires a fundamentally different runtime (e.g. a local vLLM server instead of Ollama), that is handled by writing a new `ReasoningProvider` implementation and registering it — not by modifying existing components.
- `SessionMetrics` and conversation `events.py` are the intended data sources for training signals. Persistence hooks for these will be added when the training pipeline matures.

## Compliance Rule

> Model development lives outside the backend. Sentri's inference stack depends on abstractions, not implementations. Swapping a model never requires changing the conversation, API, or runtime layers.
