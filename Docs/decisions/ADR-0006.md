# ADR-0006 — Decommissioning the World Awareness and File Monitoring Subsystem

**Status:** Accepted  
**Date:** 2026-07-09  
**Author:** Antigravity AI Partner  

---

## Context

The "world awareness" subsystem was designed to provide Sentri with real-time knowledge of the user's workspace, automatically scanning directories, syncing changes every 3 hours, and running a real-time watchdog daemon. 

While this provided rich context, it introduced several drawbacks:
1. **Database Bloat**: The filesystem index grew to over 22,200+ nodes, bloating the SQLite database file size to 14.8 MB.
2. **Resource Consumption**: Running a background thread for directory scanning and a file system watchdog daemon consumed unnecessary CPU cycles and disk I/O.
3. **Complexity**: System logs were flooded with folder and file synchronization events, overshadowing core conversational data.

## Decision

We decided to completely decommission and remove the world awareness and file monitoring subsystems from Sentri V2. 

Specifically:
1. Deleted the `app/world_model/` services folder (model builder, sync service, and watchdog).
2. Cleaned all lifecycle hooks out of the FastAPI server's startup/lifespan loop in `main.py`.
3. Removed the `watchdog` Python dependency.
4. Deleted all filesystem and event nodes from `Sentri.db`, leaving only the 19 core user memory and directive nodes.
5. Removed system event and standby session logging from `runtime_service.py`.

## Motivation

This change simplifies the codebase, dramatically improves startup latency, reduces CPU and memory overhead, shrinks the SQLite database to just 36 KB, and keeps the project focused on conversation, reasoning, memory, and code intelligence while avoiding continuous environment observation.

## Consequences

* The assistant will no longer have access to local file maps or real-time file updates.
* Memory storage is now purely semantic (user preferences, facts, and directives).
* Clean-up scripts must be maintained to ensure any future system additions do not re-introduce filesystem scanning loops.
* **Positive Consequence**: Sentri transitions from a proactive environment-monitoring architecture to an on-demand environment-access architecture.

## Compliance Rule

> Sentri V2 does not perform continuous background filesystem observation. Environment awareness is acquired on demand unless a future ADR explicitly reintroduces persistent observation for a justified use case.

## Future Considerations

Persistent filesystem observation is intentionally excluded from Sentri V2.

If future versions require environment awareness, it should be introduced through explicit, scoped capabilities (for example, monitoring a single project workspace during an active development session) rather than continuous machine-wide indexing. That prevents someone from reintroducing a desktop-wide watchdog without a deliberate architectural decision.
