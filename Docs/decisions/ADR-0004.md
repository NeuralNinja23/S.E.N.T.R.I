# ADR-0004 — Memory Retrieval Boundary

**Status:** Accepted
**Date:** 2026-07-09 (Updated: 2026-07-18)
**Author:** Sentri V2

---

## Context

Sentri's memory layer (`app/memory/`) contains graph-based long-term memory, diary summarization, and knowledge extraction. All of these require LLM calls. The question was: who owns these LLM calls, and how are they dispatched?

In V1, memory operations called a local Ollama endpoint directly using its HTTP API. This baked the Ollama URL and model name into the memory functions as explicit parameters.

## Decision

The memory layer continues to call `call_llm_direct` and `call_llm_streaming` from `app.conversation.adapter`. This is an intentional compatibility interface that abstracts the underlying LLM provider (currently Ollama with `Qwen3.5-4B-Uncensored`) behind a stable function signature.

The memory layer does **not**:
- Import `ConversationEngine`
- Import any model driver or provider implementation
- Import from `api/` or `runtime/`
- Manage model processes

The memory layer **is allowed to**:
- Accept `ollama_base_url` and `ollama_chat_model` as function parameters (legacy interface, kept for compatibility with existing callers)
- Route those parameters through `call_llm_direct` in `adapter.py`

## Motivation

- Preserves a working memory system without a full rewrite.
- `adapter.py` is the correct seam to change LLM providers — updating it propagates to all memory operations automatically.
- Keeps `app/memory/` focused on graph logic, retrieval, and summarization rather than LLM client management.

## Consequences

- If the LLM provider changes (e.g. from Ollama to a cloud inference endpoint), only `adapter.py` needs updating. Memory functions remain unchanged.
- `call_llm_direct` and `call_llm_streaming` are stable API surfaces — their signatures must not change without updating all memory callers.
- Memory functions must not bypass `adapter.py` to call any LLM directly.

## Future

With the introduction of tool calling (see ADR-0002), the reasoning provider can now execute workspace tools (file reads, code search, memory queries) as part of a conversation turn. Memory extraction could eventually be unified into this tool-calling path by exposing `remember_fact` and `search_memory` as tools — which has already been implemented. The long-term direction is to consolidate all LLM dispatch through the tool-aware reasoning loop.

## Compliance Rule

> `memory/` depends on `conversation/adapter.py`. `conversation/adapter.py` depends on the LLM provider. The LLM provider does not depend on `memory/`.
