# ADR-0001 — Conversation Engine Abstraction

**Status:** Accepted
**Date:** 2026-07-09
**Author:** Sentinel V2

---

## Context

Sentinel V1 used a cascaded pipeline: ASR → LLM → TTS. Each stage was implemented as a standalone service and called directly by the WebSocket handler. This created tight coupling between the transport layer, the speech model, and the frontend.

Replacing any one stage (e.g. switching Whisper for a better ASR) required touching the WebSocket handler, the service layer, and any test that referenced the old service.

## Decision

All communication between the API layer and any speech or reasoning model is routed exclusively through `ConversationEngine`.

The WebSocket handler (`api/websocket.py`) never imports a model implementation directly. It only calls:

```python
engine.run_voice_turn(audio_stream)
engine.run_text_turn(system_prompt, text_query)
engine.supports("streaming")
```

## Motivation

- Allows replacing MiniOmni2 with any future model (Sentinel Voice V1, vision models, etc.) without modifying the WebSocket handler, Memory layer, Runtime manager, UI, or Watchdog.
- Enforces a single entry point for all conversational interactions.
- Makes capability queries (`engine.supports("vision")`) the canonical way to branch on model features instead of `if model_name == ...`.

## Consequences

- All speech models must implement `ISpeechToSpeechModel` from `conversation/interfaces.py`.
- All text reasoning paths must be exposed through `ConversationEngine.run_text_turn()`.
- No future code outside `conversation/` may import a model implementation class directly.

## Compliance Rule

> The WebSocket handler depends on `ConversationEngine`. `ConversationEngine` never depends on `websocket.py`.
