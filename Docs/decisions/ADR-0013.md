# ADR-0013 — Capability-Based Backend Structure and API Layer Decomposition

**Status:** Accepted
**Date:** 2026-07-20
**Author:** Sentri V2

---

## Context

As SENTRI V2 grew from a prototype into a multi-module system, the `backend/app/` directory became a flat collection of interdependent files. The two core concerns of the system — **Persistent Memory** and **Conversation Intelligence** — were co-located without any enforced boundary:

- **No domain isolation:** Memory logic (graph store, verification lifecycle, context builder) and conversation logic (ASR, LLM, TTS, streaming pipeline, intent analysis) lived side-by-side with no structural separation.
- **No API layer ownership:** A single monolithic `websocket.py` file contained both connection management and all business logic for memory erasure, context retrieval, voice turn processing, and text turn processing. This violated the single-responsibility principle and made individual capabilities impossible to test, replace, or extend independently.
- **Flat file sprawl:** `capability_2/` held 18+ top-level files (e.g., `engine.py`, `adapter.py`, `events.py`, `prompt_builder.py`, etc.) in a single directory with no grouping by concern.
- **Brittle imports:** Any file needing memory or conversation features imported directly from sibling modules, creating circular dependencies and tightly coupling unrelated subsystems.

## Decision

We restructured the backend into two **named capability packages**, each owning its own internal subdirectories and a dedicated `api/` layer:

```
backend/app/
├── api/
│   ├── system_stats.py          # Global telemetry (shared)
│   └── websocket.py             # Global WebSocket gateway (delegates only)
│
├── capability_1/                # Persistent Memory
│   ├── core/                    # contracts, runtime, registry, context_builder
│   ├── infra/                   # adapter
│   ├── providers/               # provider implementations
│   ├── storage/                 # database store
│   └── api/
│       ├── memory.py            # handle_memory_erasure, retrieve_memory_context
│       └── upload.py            # document context ingestion
│
└── capability_2/                # Conversation Intelligence
    ├── core/                    # contracts, engine, interfaces, metrics, registry, session
    ├── routing/                 # intent_analysis, retrieval_planner, quick_responses
    ├── prompts/                 # prompt_builder, system_prompt, memory_provider
    ├── events/                  # event_bus, events
    ├── infra/                   # adapter, utils
    └── api/
        └── conversation.py      # process_user_turn, process_user_text_turn
```

The global `websocket.py` was reduced to a pure **connection router**: it handles WebSocket lifecycle, audio/text frame ingestion, and governance signals (pause, resume, stop, interrupt), but delegates all turn execution to the capability APIs.

## Motivation

- **Domain ownership:** Each capability owns its domain end-to-end — from storage to API surface. Changes to memory logic cannot accidentally break conversation logic.
- **Testability:** Individual capability API functions (`handle_memory_erasure`, `process_user_text_turn`, etc.) can be unit-tested in isolation without bootstrapping the WebSocket layer.
- **Replaceability:** `capability_1` can be swapped for a different memory backend (e.g., vector store, knowledge graph) without touching `capability_2`. Similarly, `capability_2` can be replaced with a different conversation engine without affecting memory APIs.
- **Navigability:** Developers can locate code by intent (`capability_2/routing/intent_analysis.py` vs `capability_2/prompts/prompt_builder.py`) rather than scanning a flat file list.
- **Scale path:** Future capabilities (e.g., `capability_3/` for tool execution or `capability_4/` for vision) can be added as peer packages following the same convention, each with their own `api/` folder.

## Alternatives Considered

| Option | Reason Rejected |
| :--- | :--- |
| Keep flat structure, add comments | Does not enforce boundaries; coupling persists at import level |
| Full microservice split | Premature for a local-first system; operational overhead outweighs gains |
| Feature-flag based conditional imports | Adds indirection without solving the co-location problem |

## Consequences

- **Positive:** Capability boundaries are now structurally enforced by the package hierarchy. The `websocket.py` surface area dropped from ~600 lines of mixed business logic to a ~270-line connection router.
- **Positive:** All 56 unit tests continue to pass with zero logic changes — the refactoring was purely structural.
- **Positive:** The evaluation simulator (`voice_eval_simulator_v5.py`) imports directly from `capability_1` and `capability_2` APIs, validating the public contract.
- **Constraint:** New API endpoints must be placed inside the appropriate `capability_N/api/` folder and then re-exported via `websocket.py` or `main.py` — not added directly to `app/api/`.
- **Constraint:** Cross-capability imports must flow upward through public `__init__.py` exports, not sideways through internal module paths.

## Compliance Rule

> All domain-specific API logic must reside inside the owning capability's `api/` subfolder; `app/api/websocket.py` is a connection gateway only and must not contain business logic.
