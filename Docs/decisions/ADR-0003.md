# ADR-0003 — Inference Runtime Manager

**Status:** Accepted (Updated from subprocess management to in-memory model lifecycle)
**Date:** 2026-07-09 (Updated: 2026-07-18)
**Author:** Sentri V2

---

## Context

In V1, MiniOmni2 ran as an independent Flask server on port `60808`. `InferenceRuntimeManager` was responsible for spawning the subprocess, probing its health endpoint, and managing its lifecycle states (`STOPPED → STARTING → LOADING_MODEL → READY → BUSY → STOPPING → FAILED`).

With the migration to the decoupled streaming pipeline (see ADR-0002), MiniOmni2 was replaced by in-process models that load directly into GPU VRAM. There is no external subprocess to manage. The role of `InferenceRuntimeManager` shifted from process orchestration to **in-memory model lifecycle management**.

## Decision

`InferenceRuntimeManager` (defined in `runtime/model_runtime.py`) now manages in-memory singleton instances of:

1. **Faster-Whisper** (ASR) — loaded via `faster_whisper.WhisperModel("base")`, GPU-accelerated with `float16` or CPU fallback with `int8`.
2. **Kokoro ONNX** (TTS) — loaded via `kokoro_onnx.Kokoro`, using ONNX Runtime with CUDA EP when available.

`InferenceRuntimeManager` exposes:
- `state: ModelState` — observable state enum (`UNLOADED → LOADING → READY → FAILED → UNLOADING`)
- `start()` — loads both models into memory on application startup
- `stop()` — unloads models and reclaims memory
- `whisper_model` — the loaded Faster-Whisper instance (used by `WhisperASRProvider`)
- `kokoro_model` — the loaded Kokoro ONNX instance (used by `KokoroTTSProvider`)

`main.py` only calls `inference_runtime_manager.start()` and `.stop()`. It has no knowledge of model weights, ONNX sessions, or VRAM allocation.

The reasoning model (Ollama) is **not** managed by `InferenceRuntimeManager`. Ollama runs as an independent system service and is accessed via HTTP by `OllamaReasoningProvider`. Its lifecycle is outside the application's control.

## Motivation

- Eliminates external subprocess management (no more Flask server spawning, health probes, or port conflicts).
- In-memory singletons load once at startup and are reused across all voice turns, eliminating per-request model loading latency.
- GPU/CPU fallback is handled transparently at load time.
- The state machine is simplified to five states matching the in-memory lifecycle.

## Consequences

- `ConversationEngine` must never call `inference_runtime_manager`. It accesses models through their provider interfaces.
- `InferenceRuntimeManager` must never import from `conversation/session.py` or `api/`.
- Providers (`WhisperASRProvider`, `KokoroTTSProvider`) reference the manager's model singletons but do not manage their lifecycle.
- If a future model requires an external process (e.g. a vision model server), it should get its own lifecycle manager rather than overloading `InferenceRuntimeManager`.

## Compliance Rule

> `InferenceRuntimeManager` owns model loading and unloading. Providers consume model instances. `ConversationEngine` is unaware of either.
